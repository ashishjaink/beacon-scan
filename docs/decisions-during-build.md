### D-02. Schema fix: `StoreSnapshot.policies.{shipping,refund}` made nullable
bluetokaicoffee.com's `robots.txt` disallows `/policies/*` and `/*/policies/*` for user-agent `*` (a store-specific customisation — the other 5 stores checked have no such rule). The collector must not fetch those paths (WO Hard Rule #3, store-collector spec "Robots and rate limits"). design.md §2 originally typed `policies.shipping`/`policies.refund` as plain non-nullable booleans, which cannot distinguish "confirmed missing" from "not checked because robots.txt disallows it" — collapsing them to `false` would be a factually wrong claim (I confirmed both policy pages return 200 by direct request; the collector just isn't allowed to check them). Fixed **before** any lane started building: `shipping`/`refund` are now `z.boolean().nullable()`, `null` meaning "not checked." `linkedFromHome` is unaffected (computed from the already-fetched homepage HTML, no extra disallowed fetch needed).

Consequence for Lane B (`engine/scorecard.ts`, Trust finding): treat `null` as its own case — `severity: "low"`, evidence names the robots.txt rule, recommendation notes that this also blocks any bot/agent that honours robots.txt (including AI shopping agents) from verifying the merchant's own policies. Only score `"high"` when a policy is confirmedly `false` (fetched, non-200), `"medium"` when present but not linked from home, `"none"` when both present and linked.

### D-03. Fixtures: `collections.json` kept complete (250 real collections); `collection.<handle>.json` recorded for a bounded subset (merch collections + top-15 by `productsCount`, 20 total)
Recording all 250 collections' product listings would mean ~250 sequential throttled requests (~2+ minutes) for fixture purposes alone, most of which are narrow marketing/filter collections. `collections.json` is recorded as the real, complete, unmodified response (public data, nothing stripped). Only a bounded, real subset gets its `/collections/<handle>/products.json` recorded. To avoid the "missing fixture file" per-collection scenario (store-collector spec) firing ~230 times and flooding `methodology.limits`, Lane A's offline collection-membership pass should emit **one aggregated** limit line (e.g. `"collection membership recorded for 20/250 collections in fixtures; rest treated as empty (fixture-recording bound, not a live-scan limitation)"`) instead of one line per missing handle. This only applies to fixtures/offline mode — a real online scan (`collect()`) still attempts every collection subject to `maxProducts`/robots/time, so the real run Ashish does later is not artificially bounded to 20.

### D-04. `src/types.ts` additions beyond the literal design.md §2 listing
Added two zod schemas design.md described only in prose: `AvailabilityDelta` (shape given in design.md §9) and `BeaconConfig` (shape given in design.md §5, referenced by name in §10's `ScanOptions.config` and function signatures but never given a zod schema). `Findings.delta` stays `z.any().optional()` exactly as design.md §2 specifies (not tightened to `AvailabilityDelta`, to stay verbatim on the frozen block). Every schema, including the two additions, has a matching `z.infer` export.

### D-05. Report internal function names: `renderHtml` / `toCsv` / `toTerminal` (not `writeCsv`/`printTerminal` as WO §3 Lane 0 text lists)

Used the Lane C/spec names for the actual stub and library wiring, since that's the authoritative, more detailed contract and matches "pure functions returning strings" — `src/cli.ts` (Lane C) is what writes/prints.

## 2026-09-22 — Lane A

### D-06. `StoreSnapshot` has no field for collector-discovered limit notes — added a non-schema `collectorLimits: string[]` passthrough property instead of editing `types.ts`
The store-collector spec repeatedly requires the collector to *record* a limit note (robots-disallowed collection positions; product-catalogue truncation; D-03's one aggregated fixture-bound note; D-02's policies-not-checked note), and `Findings.methodology.limits` is exactly the field these are meant to end up in — but that field lives on `Findings`, which only `engine/index.ts` (`analyse()`, Lane B) constructs, and `StoreSnapshot` (design.md §2, frozen) has no `limits`/notes field of its own to carry them from the collector to the engine.

Rather than edit the frozen `StoreSnapshot` schema, `collect()`/`collectOffline()` return an object that is a valid `StoreSnapshot` in every sense `StoreSnapshot.parse(...)` checks (zod's default `strip` mode silently drops unrecognised keys, so `.parse()` succeeds unchanged) **plus** an extra runtime-only property, `collectorLimits: string[]`, holding every note the collector itself produced. TypeScript allows this without a type error because both functions return a variable typed as `StoreSnapshot & { collectorLimits: string[] }` through a `Promise<StoreSnapshot>`-declared signature — structural widening on return, not a literal excess-property check. `tests/collector.test.ts` asserts on `snapshot.collectorLimits` directly (pre-`.parse()`) for every scenario that produces a note.

**Proposed contract diff for Lane I / a future design.md revision:** add an optional field to `StoreSnapshot` in design.md §2 — `collectorLimits: z.array(z.string()).optional()` — so this is a first-class, typed part of the contract instead of a documented convention. Until then: **Lane B's `analyse()` should read `(snapshot as any as { collectorLimits?: string[] }).collectorLimits ?? []` and fold it into `Findings.methodology.limits` alongside whatever the engine derives on its own.** If Lane B ran before this note was visible (parallel lanes), Lane I should wire this at integration — it's a one-line addition to `engine/index.ts`.

### D-07. Online pagination stop rule: a short page (`batch.length < limit`) also ends pagination, not only a strictly empty page
The store-collector spec's own "Store with 612 products" scenario expects exactly 3 product-page requests for 612 products at `limit=250` (250+250+112). That only holds if pagination stops as soon as a page returns fewer than `limit` items — a literal "until an empty page" reading would require a 4th, confirmatory, empty page fetch that the scenario's request count doesn't include. Implemented `fetchAllProducts`/`fetchAllCollections`/`fetchCollectionMembership` (`src/collector/shopify.ts`) to stop on `batch.length === 0 || batch.length < limit`. This is also the more standard real-world pagination approach (Shopify's `/products.json` never returns a short-then-nonempty sequence in practice). `collectOffline()`'s file-based loop is unaffected — it stops on a missing page file or an empty batch, which naturally matches this store's real `products.page1.json` (190, i.e. already short) followed by the explicitly-recorded empty `products.page2.json`.

### D-08. Minor additive (backward-compatible) option surface changes in Lane A's own files
- `collectOffline(dir, opts?: { onProgress?, now?, config? })` — Lane 0's stub signature was `collectOffline(dir: string): Promise<StoreSnapshot>`; added an **optional** second parameter so the function is independently progress-reporting/deterministic-clock testable. `src/index.ts`'s existing call site (`collectOffline(opts.offlineFixturesDir)`, one argument) is untouched and still type-checks.
- `CollectOptions.now?: () => Date` — added for the same reason to `collect()`'s options; note `src/index.ts`'s `scanStore()` does not currently thread its own `opts.now` down into the `collect(url, {...})` call it makes (only into `analyseSnapshot`/`analyse`), so live scans still use wall-clock `fetchedAt` regardless — flagging in case Lane I wants `scanStore` to pass it through for full determinism in offline/replay scenarios.

## 2026-09-22 — Lane B

### D-09. `pdp/colour-variants-without-image` severity reuses `thresholds.lowImagePct`
(Renumbered from Lane B's original "D-06" at integration — Lane A independently used D-06 for an unrelated decision since both lanes ran in parallel and couldn't see each other's entries. Content below is unchanged from Lane B's report.)
`design.md §4` lists exactly seven threshold config keys (`orphanPct, soldOutTopN, soldOutInTopCount, lowImagePct, shortDescPct, coreSizeOutPct, noCapturePct`) for eight required scorecard Findings — there is no dedicated key for `pdp/colour-variants-without-image`, and `beacon.config.json` (§5) confirms the same seven keys, not eight. Rather than inventing an unconfigured eighth threshold (which the frozen `BeaconConfig` zod schema in `src/types.ts` doesn't have a slot for either, and that schema is frozen per Hard Rule #2), `src/engine/scorecard.ts`'s `colourVariantsWithoutImageFinding()` reuses `config.thresholds.lowImagePct` to grade severity: both checks are in the same "PDP image completeness" family (one counts products with <2 images overall, the other counts colour-option products missing a per-variant image), so sharing one threshold pair is a reasonable reading rather than a schema change. No spec Scenario pins an exact severity value for this check, so this choice is unverified against a numeric assertion — flagged here for Lane I / Ashish in case a dedicated `colourVariantsPct` threshold is wanted in a follow-up change.

## 2026-09-22 — Lane I (post-integration, first real run)

### D-10. `http.ts`: added a shared cooldown gate so a 429 pauses the whole client, not just the retrying request
First real (online) scan failed hard: `RATE_LIMITED` on collection #207/225 (`test-coffee-maker`) after 206 successful sequential collection-membership fetches. Root cause found in `src/collector/http.ts`: the token bucket throttles how fast *new* requests are issued, but with `concurrency: 2`, while one request was mid-backoff from a 429, its sibling slot kept pulling fresh URLs from the queue and firing them at the normal rate — so the client never actually slowed down as a whole once the store started rate-limiting, and the per-request exponential backoff (1s→16s, max 4 retries, matching `openspec/project.md`'s "Important Constraints" exactly) couldn't outrun a sustained 429 state being kept alive by the other slot.

Fix: added a shared `cooldownUntil` timestamp inside `createHttp()`'s closure. Every 429/5xx retry sets `cooldownUntil = max(cooldownUntil, now() + waitMs)` (honouring `Retry-After` when the store sends one, same as before), and `executeThrottled()` now waits out any active cooldown *before* taking a token bucket slot — for every request, not just the one that got the 429. This changes no configured value (`rps`/`concurrency`/`maxRetries`/`timeoutMs` in `beacon.config.json`, frozen per Hard Rule #2 / design.md §5, are untouched) — it's a behavioural fix to how concurrency and backoff interact, keeping the existing numbers but making them behave as "polite" as the spec intends. `tests/collector.test.ts` (36/36) unaffected.

Recovery: the failed run's 6h disk cache (`.cache/bluetokaicoffee.com/`, 207 files) already held every successful response, so the retry after this fix reuses those and only needs the ~19 remaining collections — no need to re-fetch from scratch or to bound the online path's collection count (which would contradict D-03's explicit statement that the real run is *not* artificially bounded to a small collection subset the way offline fixtures are).

### D-11. `pdp-markers.ts`: a robots.txt-disallowed PDP now skips instead of aborting the whole sample
Second real-run failure, found immediately after D-10's fix let the scan get past all 225 collections: `ROBOTS_DISALLOWED` on `/products/all-products` crashed the run during PDP sampling (candidate 13/20). This store's `robots.txt` has a specific `Disallow: /products/all-products` rule (a real, deliberate store-specific rule — not a bug in our robots parser; confirmed by reading the raw cached `robots.txt`). The bug was in `samplePdpMarkers`'s online branch (`src/collector/pdp-markers.ts`): it called `http.get(product.url)` directly, and `http.get()` throws `BeaconError("ROBOTS_DISALLOWED", ...)` by design when a path is disallowed (correct — fetching a disallowed path at all would be the actual violation) — but nothing caught it, so one disallowed PDP among 20 candidates took down the entire scan. `fetchCollectionMembership` in `src/collector/shopify.ts` already had the right pattern (`http.allowed()` checked first, skip-and-continue on `false`) — `pdp-markers.ts`'s online path just didn't follow it. Fixed to match: check `allowed()` first, skip that one candidate via `onProgress` + `continue` on disallow, same as the offline path already does for a missing fixture file. No test regressions (`collector.test.ts` 36/36 still green — none of Lane A's own mocked scenarios happened to exercise a disallowed PDP mid-sample, which is why this didn't surface until the real store hit it).

## 2026-09-23 — Lane I (second run, +12h)

### D-12. `engine/index.ts`: `analyse()` now copies a passed `delta` onto `Findings.delta`
`diffSnapshots`/`analyseSnapshot(..., delta)` correctly computed the per-product `velocity` component from the delta all along (`restock.ts`'s `velocityComponent()`), but `analyse()`'s return object never attached the `delta` parameter itself to the returned `Findings.delta` field the frozen schema has for exactly this (`z.any().optional()`, design.md §2/§9). Harmless in practice so far (both real runs' `beacon diff` found zero flips, so there was nothing to lose), but a real gap in the P1 diff feature. Fixed: `analyse()` now spreads `...(delta ? { delta } : {})` into its return. No test regressions.

### D-13. `vitest.config.ts`: disabled file parallelism after a real, reproducible flakiness source
Running `npm test` (all 5 test files together) intermittently failed — different tests each time (`Endpoint disabled` timing out, `Burst of 429s` timing out, `Store with 612 products` getting 6 product-page fetches instead of 3) — while running any single file alone (e.g. `vitest run tests/collector.test.ts`) was consistently fast (~14s) and 100% green. Root cause: vitest's default file-level parallelism spins up one worker per test file (5 here); on this machine that meant 5 workers competing for CPU at once, and the handful of collector tests that use real `setTimeout`/`AbortController` timing (by design — `http.ts`'s backoff delay isn't clock-injectable, see the "Burst of 429s" test's own comment) occasionally lost that race: a mocked-`fetch` call took long enough under contention to trip `AbortController`'s real timeout, `rawFetchWithRetry` correctly treated that as a network error and retried, and the retry both passed (the underlying mock doesn't respect the abort signal, so the original call `it "completed"` too) — doubling the recorded call count in the pagination test, or blowing past the per-test timeout in the two timing-sensitive ones. This reproduced identically on a second full run (198s that time, one different test failing) and vanished the instant file parallelism was turned off (`fileParallelism: false` — every file still ~instant, they just don't compete with each other; two consecutive full runs afterward: 78/78 in ~14.6s both times). Also bumped the global `testTimeout` to 20000ms (from vitest's 5000ms default) as a second, independent layer of headroom. Neither change touches the frozen contracts or any application code — `beacon.config.json`'s `http.maxRetries`/`timeoutMs`/`rps`/`concurrency` are untouched.
